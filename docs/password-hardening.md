# パスワードの扱いの変更

2026年10月に、パスワードの保存方法と API での受け渡し方を変えた。DB の中身が漏れても、それをそのままログインに使われたり、元のパスワードを短時間で割り出されたりしないようにするのが目的。既存ユーザーはパスワードの再設定もログインし直しも要らない。

## 変更前は、DB の値がそのままパスワードとして通用していた

変更前の流れはこうだった。

1. ブラウザでパスワードを SHA-256 にかけ、その16進文字列を `password_hash` として送る
2. サーバーは受け取った値をそのまま `profiles.password_hash` に保存する
3. 以降の API では、送られてきた値と保存値を文字列として比較する

この方式には弱点が3つあった。

- **DB の値がそのまま認証情報になる。** 保存値を手に入れた人は、パスワードを知らなくても `password_hash` として送ればログインできた。
- **元のパスワードを割り出しやすい。** ソルトなしの SHA-256 を1回かけただけなので、よくあるパスワードなら事前計算した表から一瞬で逆引きできる。
- **URL に認証情報が載っていた。** `GET /api/user` は `id` と `password_hash` をクエリ文字列で受け取っていたため、アクセスログやブラウザの履歴に残りうる状態だった。

## 変更後は、重い計算をブラウザで、軽い照合をサーバーでする

| | 変更前 | 変更後 |
| --- | --- | --- |
| ブラウザが送る値 | `SHA-256(パスワード)` | `PBKDF2(SHA-256(パスワード))`。ソルトは `universe.mfmf.moe:` + ユーザー名、60万回 |
| DB に保存する値 | 送られてきた値そのもの | `v2$` + `SHA-256(送られてきた値)` |
| 照合 | 文字列の比較 | 受け取った値の SHA-256 を計算し、保存値と定数時間で比較 |
| localStorage | `passwordHash` に `SHA-256(パスワード)` | `passwordHash` に PBKDF2 の結果、`authVersion` に `2` |

PBKDF2 は、計算にわざと時間がかかるようにしたハッシュ関数で、総当たりで元のパスワードを探すコストを上げるために使う。サーバーでかけなかったのは、Workers の Free プランは1リクエストあたり CPU 時間が 10ms までで、しかもこのアプリはほぼすべての API でパスワードを照合しているから。60万回の PBKDF2 は 10ms に収まらない。そこで、重い PBKDF2 はログインと新規登録のときにブラウザで1回だけ計算し、サーバーは SHA-256 を1回かけるだけにした。

保存値は、ブラウザが送る値の SHA-256 になっている。そのため保存値が漏れても、それを送ってもログインできない。元のパスワードを探すには、候補ごとに60万回の PBKDF2 を回す必要がある。ソルトにユーザー名を混ぜているので、事前計算した表も使えない。

計算方法は次の3か所に同じものがある。どれかを変えるときは、ほかの2か所もそろえること。

- `frontend/src/lib/password.ts` (ブラウザ)
- `backend/src/lib/password.ts` (Worker。保存形式と照合)
- `backend/scripts/password.mjs` (移行スクリプト)

## 既存ユーザーは、何もしなくてよい

変更前の保存値は `SHA-256(パスワード)` で、これは変更後の計算の途中の値と同じになっている。だから、元のパスワードがわからなくても、保存値とユーザー名から新しい保存値を計算できる。この変換は `backend/scripts/upgrade-password-hashes.mjs` が行う。

ログイン中の端末も、変換前の値を localStorage に持っている。ページを開いたときに `authVersion` が無ければ、`AuthUpgrade` コンポーネントが公開 API でユーザー名を取ってきて新しい値に変換し、ページを1回だけ再読み込みする。変換に失敗した場合だけログアウト状態になり、その人はログインし直すことになる。

## API とサーバーの変更点

- **`POST /api/user` を追加した。** 本文に `target`、`id`、`password_hash` を入れて送ると、友達同士なら `friends` を含めて返す。フロントエンドは認証付きの取得をすべてこちらに切り替えた。
- **`GET /api/user` は公開情報だけを返す。** クエリ文字列に `id` や `password_hash` を付けても無視する。
- **CORS の設定を外した。** フロントエンドと API が同じオリジン `universe.mfmf.moe` になったので不要になった。これで、ほかのサイトのページから API を呼んでもブラウザが応答を読ませない。
- **ログインにレート制限を付けた。** 同じ IP から1分に10回までで、超えると 429 を返す。新規登録とアイコンのアップロードにはすでに付いている。
- `password_hash` というフィールド名と、各 API のレスポンスの形は変えていない。

## リリース時は、デプロイ直後に変換スクリプトを流す

新しい Worker は `v2$` 形式の保存値しか受け付けない。デプロイしてから変換が終わるまでのあいだは、既存ユーザーがログインできない。この時間を短くするため、次の順で進める。

1. PR をマージする。GitHub Actions が Worker をデプロイする (1分ほど)
2. Actions が終わったらすぐ、`backend/` で `node scripts/upgrade-password-hashes.mjs --remote` を実行する

スクリプトは変換前の値と一致する行だけを更新するので、何度実行しても結果は変わらない。`--dry-run` を付けると、対象の件数を表示し、SQL を書き出すだけで終わる。`scripts/migrate-from-supabase.mjs` も、Supabase から取り込むときに同じ変換をかけるようにした。

## まだ残っている課題

- **localStorage の値は、今もログインに使える。** 毎回の API で同じ値を送る作りは変えていないので、端末から値を盗まれれば、パスワードを変えるまでなりすませる。きちんと直すなら、有効期限つきのセッショントークンに切り替える必要がある。
- **ログインと登録は少し遅くなった。** PBKDF2 の計算に、開発用の Windows PC の Node.js で約0.2秒かかった。ブラウザの WebCrypto も同程度だが、古いスマートフォンでは1秒を超えるかもしれない。
- **パスワードの変更機能はまだ無い。** 作るときは、新しいパスワードからブラウザで同じ計算をして送ればよい。
